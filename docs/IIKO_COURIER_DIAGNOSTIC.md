# Почему назначенные курьеры не были найдены через iikoCloud API

Первичная проверка: 15 сентября 2026 года.

Права на чтение сотрудников повторно проверены: 17 сентября 2026 года.

## Краткий вывод

Назначенные курьеры передаются через iikoCloud API. Причина результата «курьеров: 0» — неправильная обработка структуры ответа и, вероятно, ограничение выборки первыми 50 заказами.

Утверждение о том, что курьеры назначаются только в локальном iikoTransport и не синхронизируются с iikoCloud, не подтверждается фактическим ответом API.

## Признаки неправильной проверки

### Получено ровно 50 заказов

Результат ровно в 50 заказов обычно означает одно из следующего:

- в запросе установлено `rowsCount: 50`;
- обработана только первая ограниченная выборка;
- проверена не вся совокупность организаций;
- выполнение остановлено после первого ответа.

При контрольной проверке только одной организации «Шумяцкого» API вернул:

- 188 заказов;
- 111 заказов с назначенным курьером.

Следовательно, выборка из 50 заказов не является полной проверкой данных за период.

### Проверено неправильное поле курьера

Курьер находится не в поле:

```text
order.courierInfo.name
```

Правильный путь:

```text
wrapper.order.courierInfo.courier.name
```

Структура ответа выглядит следующим образом:

```json
{
  "ordersByOrganizations": [
    {
      "orders": [
        {
          "order": {
            "courierInfo": {
              "courier": {
                "id": "COURIER_ID",
                "name": "COURIER_NAME",
                "phone": "COURIER_PHONE"
              },
              "isCourierSelectedManually": false
            }
          }
        }
      ]
    }
  ]
}
```

## Правильный пример парсинга

```python
for group in response.get("ordersByOrganizations", []):
    for wrapper in group.get("orders", []):
        order = wrapper.get("order") or {}
        courier_info = order.get("courierInfo") or {}
        courier = courier_info.get("courier") or {}
        courier_name = courier.get("name")
```

Проверка должна учитывать, что `courierInfo` или вложенный объект `courier` могут иметь значение `null`, если курьер для конкретного заказа ещё не назначен.

## Результаты контрольных проверок

Проверка по всем доступным организациям за двухдневный период ранее показала:

- 1280 полученных заказов;
- 756 заказов с назначенным курьером;
- отсутствие ошибок iikoCloud API.

Повторная проверка одной организации «Шумяцкого» показала:

- 188 полученных заказов;
- 111 заказов с назначенным курьером;
- наличие значения по пути `order.courierInfo.courier.name`.

## Что необходимо исправить

Для корректной проверки требуется:

1. Получать заказы по всем необходимым организациям.
2. Не ограничивать итоговую проверку первыми 50 заказами.
3. Обрабатывать все элементы массива `ordersByOrganizations`.
4. Обрабатывать все элементы вложенного массива `orders`.
5. Читать имя курьера из `order.courierInfo.courier.name`.
6. Не считать отсутствие курьера у отдельных заказов отсутствием данных о курьерах во всём API.

После этих изменений назначенные курьеры должны корректно определяться в ответах iikoCloud API.

## Проверка доступа приложения к сотрудникам

У текущего приложения iiko есть фактический доступ на чтение справочников сотрудников. Это проверено реальными запросами с сохранёнными `API Login`, `App ID` и `Client Secret` приложения.

Во время проверки персональные данные не выводились: для общего списка сотрудников запрашивалось только поле `id`, а результат оценивался по HTTP-статусу и счётчикам ответа.

### Фактические результаты

| Метод | Назначение | Результат |
|---|---|---|
| `POST /api/1/employees/couriers` | Курьеры доступных организаций | HTTP 200, получено 10 записей |
| `POST /api/employees/v1/employee/list` | Общий список сотрудников | HTTP 200, `totalCount: 4540` |
| `POST /api/employees/v1/positions/list` | Справочник должностей | HTTP 200, `totalCount: 99` |
| `POST /api/employees/v1/attendance/list` | Фактические явки сотрудников по организации и периоду | HTTP 200 по всем 10 организациям, ошибок нет |

Приложению доступны 10 организаций. Дополнительная настройка прав со стороны интегратора для этих четырёх методов сейчас не требуется.

### Получение списка курьеров

```http
POST /api/1/employees/couriers
Authorization: Bearer ACCESS_TOKEN
Content-Type: application/json
```

```json
{
  "organizationIds": [
    "ORGANIZATION_ID"
  ]
}
```

В ответе используется массив `employees`. Этот метод относится к группе ограничений iiko `Drivers: dictionaries` и возвращает сотрудников, являющихся курьерами в указанных организациях.

### Безопасная проверка общего списка сотрудников

```http
POST /api/employees/v1/employee/list
Authorization: Bearer ACCESS_TOKEN
Content-Type: application/json
```

```json
{
  "filters": [],
  "fields": ["id"],
  "limit": 1,
  "offset": 0
}
```

Ответ содержит:

- `items` — запрошенную страницу сотрудников;
- `totalCount` — общее количество подходящих записей;
- `limit` и `offset` — параметры пагинации.

Метод поддерживает поля `id`, `code`, `firstName`, `lastName`, `middleName`, `name`, `phone`, `email`, `cardNumber`, `mainRoleId`, `roleIds`, `isSystem`, `isFired`, `hireDate`, `fireDate`, `note`, `mainOrganizationId`, `organizationIds` и `responsibleForOrganizationIds`.

Следует запрашивать только поля, действительно необходимые сценарию. Телефоны, email, номера карт и другие персональные сведения нельзя выводить в журналы диагностики.

### Получение должностей

```http
POST /api/employees/v1/positions/list
Authorization: Bearer ACCESS_TOKEN
Content-Type: application/json
```

```json
{
  "filters": [],
  "limit": 100,
  "offset": 0
}
```

Метод возвращает страницу должностей и общий счётчик `totalCount`.

## Проверка доступа к сменам поваров

22 сентября 2026 года текущими доступами приложения выполнена read-only проверка фактических явок сотрудников. Использован метод из актуальной схемы iikoCloud API:

```http
POST /api/employees/v1/attendance/list
Authorization: Bearer ACCESS_TOKEN
Content-Type: application/json
```

Пример запроса для одной организации:

```json
{
  "organizationId": "ORGANIZATION_ID",
  "startAt": "2026-09-21T00:00:00",
  "endAt": "2026-09-23T00:00:00",
  "limit": 1000,
  "offset": 0,
  "shouldIncludePaymentDetails": false
}
```

Метод возвращает фактические явки в пределах одной организации. Основные поля ответа:

- `employeeId` — идентификатор сотрудника;
- `roleId` — идентификатор должности сотрудника в этой явке;
- `organizationId` и `organizationName` — подразделение;
- `startAt` и `endAt` — подтверждённое начало и окончание явки;
- `personalStartAt` и `personalEndAt` — время отметки сотрудника на POS;
- `isClosed` — признак закрытой явки;
- `attendanceTypeId` и `attendanceTypeCode` — тип явки.

Платёжные данные для нашей задачи не нужны. Всегда передавать `shouldIncludePaymentDetails: false` и не сохранять сведения о ставках или начислениях.

### Фактический результат проверки

За период с 21 по 23 сентября 2026 года:

- проверены все 10 доступных организаций;
- получено 272 явки сотрудников;
- 97 явок относятся к кухонным должностям;
- 126 явок в ответе числились открытыми;
- 54 открытые явки относятся к кухонным должностям;
- найдено 54 уникальных сотрудника кухни с открытой явкой;
- имена успешно разрешены через `/api/employees/v1/employee/list` для всех 54 сотрудников;
- ошибок API не получено.

Числа отражают состояние iiko на момент запроса и не должны использоваться как постоянные тестовые ожидания.

### Как определять поваров

1. Получить справочник должностей через `/api/employees/v1/positions/list`.
2. Исключить должности с `isDeleted: true`.
3. Сформировать разрешённый набор идентификаторов кухонных должностей.
4. Сопоставить `attendance.roleId` с этим набором.
5. Сопоставить `attendance.employeeId` с сотрудником из `/api/employees/v1/employee/list`.

При диагностике по названиям были найдены 21 кухонная должность, включая поваров разных категорий, старшего повара, су-шефа, шеф-повара, пиццемейкера и повара-стажёра.

Поиск по подстрокам `повар`, `сушист`, `кух`, `пицц`, `шеф` допустим для первоначального обнаружения, но в рабочей реализации нельзя полагаться только на текст названия. Названия могут быть изменены клиентом. Следует сохранить и настраивать список разрешённых `positionId` либо предоставить его выбор в админке.

Для сопоставления сотрудников запрашивать только минимальные поля:

```json
{
  "filters": [],
  "fields": ["id", "name"],
  "limit": 1000,
  "offset": 0
}
```

Нужно обрабатывать все страницы списка сотрудников. ФИО разрешается отображать авторизованному администратору, но нельзя писать в технические логи вместе с телефонами, email, номерами карт или другими лишними персональными данными.

### Открытая смена

Для получения открытых явок можно добавить в запрос:

```json
{
  "isClosed": false
}
```

Открытая явка означает, что `endAt` отсутствует. Это не всегда гарантирует, что сотрудник физически продолжает работать: возможна незакрытая или ошибочно оставленная явка. В интерфейсе следует использовать формулировку «Открытая явка в iiko», а не безусловное «Сейчас работает».

### Фактическая явка и плановое расписание

`/api/employees/v1/attendance/list` возвращает фактические явки, а не плановый график. В актуальной публичной OpenAPI-схеме обнаружены методы явок и проверки/изменения личной смены, но отдельного read-only метода получения планового расписания сотрудников нет.

Поэтому в текущем контуре можно достоверно показать:

- кто открыл явку;
- в каком подразделении;
- с какой должностью;
- когда сотрудник отметился;
- закрыта ли явка и когда.

Нельзя утверждать, что через этот метод получено назначенное на будущее расписание. Если бизнес-задача требует плановых смен, необходимо отдельно согласовать источник: iikoWeb, иной API iiko или выгрузку, доступную интегратору.

### Требования к будущему разделу «Смены поваров»

- только read-only запросы;
- выбор даты или периода с разумным ограничением;
- последовательный запрос явок по каждой организации;
- пагинация при `totalCount > limit`;
- сопоставление должностей по настраиваемому списку `positionId`;
- вывод ресторана, имени, должности, времени начала/окончания и признака открытой явки;
- явная подпись «Фактические явки iiko», чтобы не путать их с плановым расписанием;
- `shouldIncludePaymentDetails: false`;
- отсутствие ФИО и других персональных данных в диагностических логах;
- отсутствие вызовов `attendance/create`, `attendance/update`, `attendance/delete`, `shift/clockin` и `shift/clockout`.

## Текущее состояние нашей реализации

Необходимо различать права приложения и уже написанную функциональность:

- доступ iiko API к курьерам, сотрудникам и должностям подтверждён;
- доступ к фактическим явкам сотрудников подтверждён по всем 10 организациям;
- общий метод `IikoClient.post()` технически позволяет выполнять эти read-only запросы;
- текущая страница iiko в админке пока не содержит отдельного справочника сотрудников;
- текущая страница iiko в админке пока не содержит раздела фактических явок или смен поваров;
- сейчас в интерфейсе отображается только имя курьера, назначенного конкретному заказу, из `order.courierInfo.courier.name`;
- получение списка сотрудников не требует изменения заказов и должно оставаться отдельной операцией только на чтение.

Если будет добавлен раздел сотрудников, нужно обязательно реализовать пагинацию, фильтрацию по организациям и признаку `isFired`, минимальный набор возвращаемых полей и запрет записи персональных данных в технические логи.
